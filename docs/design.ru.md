# Как это устроено

## В чём сложность задачи

Хук видит ровно одно: строку команды до запуска. Ему нужно ответить на один
вопрос — напечатает ли эта команда учётные данные — и ответить без разбора
синтаксиса оболочки, достаточно быстро, чтобы стоять перед каждой командой.

Два очевидных подхода не годятся:

- **Сравнивать имя команды.** `env` запрещён, но при простом сравнении начала
  строки мимо проходит `env | grep KEY`, а `rtk env` проходит мимо любого
  такого сравнения.
- **Искать слово в любом месте строки.** Тогда запрещённой окажется
  `awk '/env|set/ {print}'`, а регулярное выражение со словом `history`
  заблокирует команду, в которую оно вписано. Через час такую проверку
  выключают.

Поэтому проверка идёт в два прохода, и каждый смотрит на свою версию строки.

## Проход A — команды, печатающие окружение

Сначала из текста убирается всё, что стоит в кавычках:

```
jq -r '.a | select(.k|test("^(env|set)"))' f.json
    ↓ содержимое одинарных и двойных кавычек заменяется на Q
jq -r Q f.json
```

И только потом строка делится по разделителям оболочки (`|`, `||`, `&&`, `;`,
`&`), а у каждого куска смотрится первое слово. Слово внутри программы в
кавычках к этому моменту уже удалено, поэтому принять его за команду нельзя.

Это разделение появилось не из общих соображений. До него `secrets-guard`
заблокировал ту самую команду, которая правила его собственные настройки:
в фильтре `jq`
стояло `test("^(env|printenv|set)")`, а при делении по `|` из этого получаются
голые слова `printenv` и `set`.

Обёртки пропускаются до чтения имени, поэтому распознаются и `sudo env`, и
`rtk env`, и `time env`:

```
sudo rtk env    →  пропустить sudo, пропустить rtk, смотреть env
```

Кусок, который вообще не похож на имя команды — начинается с `"`, `=`, `{`,
`[`, `$` или `*`, — пропускается, а не разбирается наугад.

### Где проходит граница

| Запрещено | Разрешено | Почему |
|---|---|---|
| `env` | `env VAR=1 cmd` | Вторая форма задаёт переменную одной команде и ничего не печатает. |
| `printenv` | `printenv PATH` | Обращение к одной переменной по имени — как раз то поведение, которое нужно поощрять. |
| `export -p` | `export PATH=/x` | `-p` перечисляет всё, присваивание не перечисляет ничего. |
| `set` | `set -e` | `set` без аргументов печатает все переменные оболочки. |
| `declare` | `declare X=1` | То же самое. |
| `history` | `helm history`, `docker history` | Благодаря пропуску обёрток решение принимает первое слово. |

## Проход B — файлы, где лежат учётные данные

Проход B требует совпадения сразу по двум признакам: есть читающая команда
(`cat`, `head`, `tail`, `less`, `strings` и подобные) и есть путь, похожий на
хранилище секретов (`.env`, `~/.bashrc`, `*.pem`, `id_rsa`, `/proc/N/environ`,
`.aws/credentials`, `.kube/config`).

Ищутся они в разных версиях строки, и в этом всё дело:

- **команда — в тексте без кавычек**: она должна быть настоящей командой;
- **путь — в исходном тексте**: он часто стоит в кавычках, и проход A его бы
  удалил.

Требование обоих признаков сразу удерживает число ложных отказов низким:
в `cat README.md` нет пути к секретам, а `ls ~/.aws/credentials` ничего не
читает.

Поиск команды в тексте без кавычек — это то, что не даёт обычной прозе влиять
на решение. Вот сообщение коммита:

```bash
git commit -m "docs: cat .env ends the same way"
```

Здесь есть и читающая команда, и путь к секретам, и прежняя версия такой коммит
запрещала. Но это слова в аргументе, а не команда: после удаления кавычек они
исчезают раньше, чем команда будет найдена.

Шаблону `.env` нужна граница слева, иначе он срабатывает на обычном тексте.
Настоящий случай из работы над этим репозиторием:

```bash
jq -r '.permission.bash.env' opencode.json | head
```

В `bash.env` есть подстрока `.env`, а `head` — читающая команда, поэтому шаблон
без границы запретил совершенно безопасную команду. Теперь перед `.env` должен
стоять пробел, кавычка, косая черта или знак `=`.

## Отказ в сторону разрешения

Если на вход пришёл не JSON, или в системе нет `jq`, или поле команды пустое —
проверка завершается с кодом 0 и команда выполняется. Инструмент, который ломает
работу ассистента при любой неожиданности, рано или поздно удаляют, а удалённый
не защищает уже ни от чего.

Узкий путь — это как раз запрет: код 2 и сообщение в поток ошибок, которое
ассистент показывает модели. Во всех остальных случаях работа продолжается.

## Зачем в комплекте файл правила

Отказ в команде, которая модели кажется нужной, порождает повторные попытки:
другое написание, потом ещё одно — пока модель не сдастся или не найдёт
лазейку. Правило, которое ставится рядом с `secrets-guard`, называет замену, поэтому
первый же отказ закрывает вопрос:

```
safe-env                      # всё окружение, значения секретов скрыты
echo "$ANTHROPIC_MODEL"       # одна переменная, когда известно имя
```

`secrets-guard` — это ворота, правило — табличка рядом с ними. Одно не заменяет
другое.

## Ключи приходят из родительской оболочки

Знать об этом стоит: это объясняет случай, который иначе выглядит загадочно —
ключ есть в окружении ассистента, но его нет ни в одном файле настроек
оболочки.

Ассистент делает снимок окружения один раз, при запуске. Переменная,
экспортированная в оболочке, из которой его запустили, остаётся во всех его
командах до конца сессии — даже после того, как строку с экспортом убрали из
`.bashrc`. Это проверено чтением `/proc/<pid>/environ` родительского процесса.

Чтобы убрать её по-настоящему: выйти из ассистента, открыть чистую сессию
оболочки, убедиться, что переменной нет (`safe-env | grep NAME`), и запустить
ассистента заново.

## Чего эта защита не делает

- Она не читает **вывод** команд. Программа, которая сама печатает свои
  настройки вместе с ключами, вне её досягаемости.
- Это не изолированная среда. Тот, кто намеренно хочет прочитать значение,
  может его закодировать, перевернуть или сначала записать в файл. Цель здесь —
  обычная случайность, а случается на практике именно она.
- Она ничего не меняет в самих ключах. Если ключ попал в журнал сессии, помогает
  только выпуск нового.
