1. КРАТКАЯ СУТЬ
--------------------------------------------------------------------------------
Пароль в открытом виде прошёл через PostToolUse-хук secrets-redact и лёг в
транскрипт сессии нетронутым.

При этом тот же самый шаблон строки, проверенный отдельно через десять минут в
той же сессии, маскируется корректно. То есть правило подходит, хук установлен
и работает — но на конкретном вызове он результата не изменил.

Причину по имеющимся артефактам установить нельзя: у хука нет журнала
срабатываний, поэтому «шаблон не подошёл» и «хук не был вызван» снаружи
неразличимы.

В выводе среди прочего пришла строка вида:

4. ДОКАЗАТЕЛЬСТВА
--------------------------------------------------------------------------------

4.1 Собственный сканер репозитория подтверждает утечку

  $ /home/env2hell/tools/scan-transcripts \
      --path /root/.claude/projects/-AI-P-azure/ --quiet

      (1 line(s) with a credential)

  scanned 1 file(s); 1 with findings, 1 line(s) in total

4.2 В том же файле рядом лежат КОРРЕКТНО замаскированные строки

  Подсчёт первых символов после метки, по транскрипту:

  $ rg -o 'BasicAuth__Password=[^ "\\]{0,4}' <транскрипт> | sort | uniq -c

  Наблюдалось четыре группы:
    - одна строка   — фрагмент самого regex из команды, не данные
    - три строки    — вид "BasicAuth__Password=<RED", то есть замаскировано
    - девять строк  — синтетика из проверки 4.3, секретом не является
    - ДВЕ СТРОКИ    — начало реального значения, в открытом виде

  Три замаскированные строки — результат проверки 4.3, выполненной в ТОЙ ЖЕ
  СЕССИИ примерно через десять минут после инцидента. Между двумя моментами
  ничего не переустанавливалось и не перенастраивалось.

  Это и есть суть находки: один и тот же хук в одной и той же сессии на одном
  вызове сработал, а на другом — нет.


4.3 Тот же шаблон маскируется корректно

  Проверка выполнялась на синтетических значениях той же формы, что и реальное:
  десять символов, буквы обоих регистров и цифры, без узнаваемого префикса
  провайдера. Конкретные строки здесь не приводятся намеренно — файл не должен
  становиться постоянным ложным срабатыванием для собственного сканера
  репозитория.

  Проверялись четыре формы:

    1. метка и значение без окружения          BasicAuth__Password=<значение>
    2. закомментированная строка YAML          # - BasicAuth__Password=<значение>
       с ведущими пробелами и завершающим       (точная форма из инцидента)
    3. значение вдвое длиннее
    4. метка в нижнем регистре                 password=<значение>

  Схема проверки:

    out=$(printf '%s\n' "$s" | /root/.local/bin/secrets-redact 2>/dev/null \
          || printf '%s' "$s")
    [ "$out" != "$s" ] && echo "ЗАМАСКИРОВАНО" || echo "пропущено"

  Результат: все четыре формы — ЗАМАСКИРОВАНО. В третьей форме значение было
  заменено на "<REDACTED:N>", то есть сработал именно механизм замены, а не
  случайное отличие строк.

  Вывод: второй тир правил покрывает эту строку. Метка BasicAuth__Password на
  строке присутствует, длины значения достаточно, комментарий и отступ помехой
  не являются.

  Оговорка к методике: в этой проверке текст подавался на stdin напрямую, а не
  в виде hook-JSON, который присылает Claude Code. Возможно, внутри скрипта это
  другой путь исполнения. Проверку через реальную форму hook-JSON провести
  стоит отдельно — см. раздел 7.

6. ЧТО ОСТАЛОСЬ НЕИЗВЕСТНЫМ
--------------------------------------------------------------------------------
Почему именно на этом вызове хук не изменил результат.

Отличия этого вызова от последующих успешных:
  а) вывод пришёл из внешнего процесса ssh, а не из локальной команды
  б) внутри использовался heredoc <<'EOF', переданный в 'sudo -n bash -s'
  в) в команде присутствовало перенаправление 2>&1 на уровне SSH
  г) вывод содержал 60 строк смешанного контента, а не одну строку

Какая из этих черт значима — из артефактов не следует. Отличить
"шаблон не подошёл" от "хук не был вызван" снаружи невозможно: у
secrets-redact нет журнала срабатываний, а каталог /tmp/secrets-redact/
на момент разбора был пуст.

Осознанно НЕ утверждается никакая причина. Предположение, записанное как
факт в отчёте об утечке секрета, хуже отсутствия отчёта.


7. КАК ВОСПРОИЗВЕСТИ
--------------------------------------------------------------------------------
Требуется удалённый хост с доступом по SSH и ключом без пароля.

  1. Положить на удалённый хост файл, например /tmp/t.yml:

       services:
         x:
           environment:
             # - BasicAuth__Password=<любое значение из 10 символов: буквы обоих регистров и цифры>

  2. В Claude Code выполнить Bash-вызов ровно такой формы:

       SSH="ssh -i <key> -o BatchMode=yes user@host -p <port>"
       timeout 60 $SSH 'sudo -n bash -s' <<'EOF' 2>&1
       cat /tmp/t.yml
       EOF

  3. Проверить транскрипт:

       rg -o 'BasicAuth__Password=[^ "\\]{0,4}' \
          ~/.claude/projects/<project>/*.jsonl | sort | uniq -c

  Ожидаемое поведение: значение заменено на <REDACTED:N>.
  Наблюдаемое в инциденте: значение в открытом виде.

  Контрольная проба — тот же файл, но прочитанный локально:

       cat /tmp/t.yml

  Если локальное чтение маскируется, а чтение через SSH-heredoc нет,
  механизм локализован.


8. ЧТО ПРЕДЛАГАЕТСЯ ДОБАВИТЬ
--------------------------------------------------------------------------------

8.1 Журнал срабатываний (главное)
  Сейчас невозможно отличить три состояния:
      - хук не вызван
      - хук вызван, шаблон не подошёл
      - хук вызван, шаблон подошёл, замена применена
  Минимально достаточно одной строки на вызов в
  $XDG_STATE_HOME/env2hell/redact.log: время, инструмент, размер входа,
  число замен. Без значений.

  Именно отсутствие этого журнала не даёт закрыть находку.

8.2 Тест на форму hook-JSON, а не только на текст
  Проверка в 4.3 подавала текст на stdin. Реальный путь — JSON от Claude Code.
  В tests/ стоит завести кейс, который подаёт полный hook-JSON с полем
  вывода, содержащим многострочный текст с секретом внутри.

8.3 Кейс на вывод внешнего процесса
  Отдельный тест: результат команды, которая сама запускает ssh/docker/kubectl
  и возвращает чужой stdout. Это самый частый способ, которым конфиг чужой
  машины попадает в сессию.

8.4 Упоминание в README
  Если после 8.1 окажется, что путь через внешний процесс действительно не
  покрыт, это стоит назвать в разделе ограничений прямо, а не оставлять
  читателю вывод "раз хук стоит, значит вывод чистый".
